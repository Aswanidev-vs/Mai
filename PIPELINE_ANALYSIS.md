# Mai — Deep Codebase & Pipeline Analysis

> Generated by static analysis of the working tree on branch `v1` (HEAD `a22a3d3`, plus a modified `docs/index.html`).
> Method: SCOPE → GATHER (4 parallel subsystem traces + direct reads) → STRUCTURE → SYNTHESIZE → VALIDATE (every high-impact claim cross-checked against source; `go build ./cmd/mai` and test-binary compilation both pass).
> This document describes **what the code actually does**. Where the design docs disagree with the code, the code wins and the gap is called out in §8.

---

## 0. TL;DR

Mai is an offline, Go-based voice assistant with a 3D VRM companion. There are **two binaries** and **three overlapping "modes"**:

- `mai.exe` — the whole assistant: audio pipeline, agent/cognition, WebSocket server, static UI.
- `transparent.exe` — a Windows-only WebView2 overlay that renders the same avatar on the desktop.

| Mode | Trigger | Reality |
|---|---|---|
| **Legacy** | `agentic.enabled: false` | Wake → VAD → streaming ASR → regex parser / Ollama → TTS. No event bus, no cognition. |
| **Agentic** | `agentic.enabled: true` (current default) | `Orchestrator` + event bus + routing funnel + ReAct + memory + proactive loop. The legacy regex parser survives as a fast path *inside* the orchestrator. |
| **Companion** | `--companion` or `server.enabled: true` | A browser/overlay client attaches to the same event bus and mirrors state, audio and emotion. Not a separate pipeline — a presentation layer. |

**The three real pipelines:**
1. **Audio/voice** (`cmd/mai/main.go` + `audio*.go`, `aec.go`, `denoise.go`, `asr_stream_worker.go`, `tts_batch.go`, `internal/tts/pocket`) — a single-writer, lock-free-ish signal chain with AEC, a *hard* TTS→ASR gate, and barge-in.
2. **Agent/cognition** (`internal/agent`, `internal/cognition`, `internal/session`, `internal/personality`, `internal/memory`, `internal/tools`) — a routing funnel into either a streaming conversation path or a 3-iteration ReAct loop.
3. **Companion/avatar** (`internal/server`, `internal/server/static/js`, `transparent/`) — a JSON-RPC-ish WebSocket bus that fans events out to a Three.js VRM renderer and/or an overlay.

**Current runtime profile (`config.yaml`):** streaming **Nemotron 3.5 0.6B int8** ASR, **Pocket** TTS (with Supertonic/Kokoro/ZipVoice alternatives), local **Ollama `qwen3.5:4b`**, **DPDFNet** denoising, **Silero** VAD, **Zipformer** KWS for "Mai"/"Hey Mai", agentic **on**, server on port **8080**, vision and MCP **off**.

## 2. Boot & wiring — `cmd/mai/main.go`

`main()` (`:62`) is a single long function; initialization order is explicit:

1. Flags: `-config` (default `config.yaml`), `-test-cloud`, `-companion` (`:68-74`).
2. Load `.env`, read + YAML-parse config, resolve `${ENV}` references, apply sampling defaults (temperature 0.55 / top_p 0.85 / max_tokens 250) (`:65-98`).
3. Root context + the atomics that remain authoritative for the audio path: `isSpeaking`, `ttsPlaying`, `stopPlayback`, `lastTTSEndNano`, `startupTTSActive`, `ttsDrainTail=300ms` (`:111-149`).
4. Timing constants: post-TTS AEC window 2500 ms, VAD endpoint backstop 1600 ms, max turn 12 s, barge-in warmup 400 ms / margin 2.5× / sustain 150 ms / echo-coherence max 0.7 (`:143-194`).
5. Create `session.Manager`, echo canceller (4096 taps), denoise gate, and the `micPipe atomic.Pointer[audioPipeline]` with `submitAudioFrame` as the single ingress for local **and** browser mic (`:203-272`).
6. **Sherpa init**: (1) KWS spotter + keyword stream (`:334-358`), (2) Silero VAD + 10 s circular buffer (`:360-381`), (3) ASR recognizer selected by `asr.active_model` — qwen3 (offline), nemotron (streaming), omnilingual (offline), transducer (streaming) (`:383-497`), (4) decoupled `streamingASR` worker queue depth 128 (`:499-511`).
7. **TTS init** (`:545-870`): Sherpa `OfflineTts` (Supertonic/Kokoro/Pocket/ZipVoice) or the custom `internal/tts/pocket/engine.go` (5 ONNX sessions via `onnxruntime_go`, SentencePiece tokenizer); voice cloning reference WAV; voice-colouring chain (pitch shift → exciter → 3.8 kHz clarity bell → loudness normalize → limiter).
8. Start TTS renderer + player goroutines and the sentence queues (`ttsSentCh` cap 64, `ttsRenderedCh` cap 4) (`:871-1294`); optional startup "System ready" phrase.
9. Automation + WhatsApp workflow init (`:1328-1346`).
10. **If `agentic.enabled`** (`:1355-1563`): event bus → LLM factory/`HybridProvider` → 4 memory stores → tool registry (10 built-ins + optional MCP) → `ReActLoop` → `Orchestrator` → `orch.Start(ctx)` → `perception.Bridge` → WebSocket server (if `--companion`/`server.enabled`) → bus subscriptions (interrupt, TTS, browser mic frames, mic pause/resume).
11. Audio capture init (`newAudioCapture(16000, 1)`) (`:1567-1571`).
12. **Legacy worker** (`workerChan` cap 10) reading `Task{Text, IsReasoning}` (`:1573-1686`) — only used when `agentBridge == nil`.
13. State machine (`StateWakeWord` / `StateListening`), `finalizeTurn`, `runListening`, `handleAudioFrame` installed into the pipeline (`:1688-2501`).
14. Start capture; block on SIGINT; shutdown drains TTS and waits for all goroutines (`:2509-2560`).

**Key architectural fact:** the agentic layer is *additive*. The legacy audio path and the orchestrator share the same audio front end; `finalizeTurn` chooses one at runtime (`:1866-1875`).

### 3.2 The hard TTS→ASR gate (recent commit focus)

The current design deliberately prevents **any** frame captured while `ttsPlaying == 1` from entering ASR — *including a verified barge-in frame*. Only three `submitASRFrame` call sites exist (`main.go:1951, 2395, 2423`), none inside the TTS branch. `beginBargeInTurn` (`:2106-2116`) explicitly submits no audio, sacrificing the first words of an interruption to keep Mai's own voice out of STT with certainty. The gate is held through the device buffer tail (`ttsDrainTail = 300 ms`) and a 2,500 ms post-TTS AEC window. This is the net effect of commits `a7cec80`, `62574de`, `7bbe128` and partially reverses the earlier speech-preservation work in `44edf11` — an intentional, documented tradeoff (`main.go:2098-2108`).

### 3.3 Output chain (text → audio → echo reference)

```
Agent TTSFunc / speak() → ttsItem → ttsSentCh(64)      main.go:899-919, 1439-1448
   ▼ renderer goroutine  main.go:1116-1183 (prefetch; Pocket sentence batching)
synthesize (sherpa OfflineTts or pocket.Engine)
   → colourVoice: pitchShift → exciter → clarity bell → loudness normalize → limiter
   → ttsRenderedCh(4)
   ▼ player goroutine  main.go:1192-1294 (serializes whole turns)
   ├─ sets isPlaying=1, ttsPlaying=1; AEC refBuffer.Clear + Reset; lag budget → 3 frames
   ├─ publish tts.chunk (base64 int16, 44.1 kHz, muted mirror + duration_seconds)
   ├─ local speaker via playAudioStreaming(ctx, 44100, &stopPlayback)  audio.go:476-632
   │     └─ device callback resamples played audio 44.1k → 16k and pushes it into
   │        global refBuffer — the AEC reference contains exactly what the speaker played
   └─ closeTurn: sleep 300 ms, set lastTTSEndNano, clear gates, restore idle lag 16
```

On barge-in, `flushBargeIn` (`audio.go:560-578`) advances the reference timeline with silence (via `markFlushedSilence`) so the canceller does not replay discarded audio.

### 3.4 Concurrency / timing inventory

| Mechanism | Value | Source |
|---|---|---|
| Capture period | 400 frames / 25 ms, 16 kHz | `audio.go:54, 130-154` |
| Mic queue | cap 16, lag budget **3 frames while playing** / **16 idle** | `audio_pipeline.go:37,53,58` |
| AEC | 4096 taps = 256 ms, NLMS μ=0.5; coherence scan ~1.6 M MAC | `aec.go:255-379` |
| Denoise queue | cap 4 frames (~100 ms), DPDFNet worker | `denoise.go:333-430` |
| ASR queue | 128 frames (~3.2 s), own decode goroutine | `asr_stream_worker.go:43-70` |
| VAD | Silero, 512-sample (32 ms) window, 10 s circular buffer | `main.go:360-381` |
| Endpoint backstops | decoder silence rules 2.4/1.2/20 s; app 1600 ms silence + 12 s cap | `config.yaml:139-153`, `main.go:152-162` |
| Follow-up window | 15 s | `main.go:2373` |
| Post-TTS AEC window | 2500 ms | `main.go:147-150` |
| Playback ring | 200 ms; 5 ms stop-watcher; 200 ms chunk slices to browser | `audio.go:276-299, 476-632`, `main.go:1033-1050` |

Backpressure is uniformly **drop-oldest** with explicit dropped-frame counters and rate-limited warnings — the system chooses latency over completeness.

### 3.5 sherpa-onnx binding

Main ASR/KWS/VAD/TTS uses **cgo** through `github.com/k2-fsa/sherpa-onnx-go v1.13.5` → `sherpa-onnx-go-windows` (`import "C"`, links `sherpa-onnx-c-api`/`onnxruntime`). Runtime DLLs sit beside `mai.exe`. The custom Pocket TTS engine is a **separate** binding: `onnxruntime_go` via purego/dlopen with an explicit shared-library path (`internal/tts/pocket/engine.go:144-152`). Two ONNX Runtime loading paths coexist; repo comments warn about a stale System32 ORT 1.17 shadowing 1.27 (`denoise.go:59-88`).

## 4. Pipeline B — Agent / Cognition

### 4.1 Routing funnel (`Orchestrator.HandleInput`, `internal/agent/loop.go:403-570`)

```
perception.audio.transcription / perception.vision.scene
   ▼ handleTranscription (loop.go:1753-1784) → HandleInput(context.Background(), {"text": ...})
   │
   1. user-turn hooks (WhatsApp guard), echo + repeat guards
   2. detectAction → companion.dance / companion.action events
   3. greeting fast path (cached, no LLM, Spoken=false)
   4. status=thinking, interrupt processing flag, latency timer
   5. emotion: decay → text detect → merge prosody → publish emotion.detected
   6. user model + memory writes + proactive.RecordAction
   7. ClassifyInterrupt → RequestInterrupt if >= HIGH
   8. skillsRunner.TryRun (keyword skill) → short-circuit
   9. DirectAction = executor.ParseAndExecute (regex fast path)
  10. PromptEngine.ClassifyTask:
        conversation | greeting | creative → handleConversation (streaming)
        everything else                    → ReActLoop.Execute (max 3 iterations)
  11. adaptResponse + response storage
```

### 4.2 Conversation vs ReAct

- **Conversation path** (`loop.go:826-1125`): optional RAG + procedural-pattern + `web_research` grounding; prefers `ChatStreamer.StreamChat` with verbatim history and a *volatile tail* on the final user message (time of day, profile, RAG facts, task tag, emotion note, persona anchor) — KV-cache-friendly. Falls back to a flat prompt via `PromptEngine.BuildPrompt`. On each sentence boundary, `publishTTS` emits speech with emotion-adapted TTS params; `[ACTION]` tags in the output fall back to the regex parser or ReAct.
- **ReAct path** (`internal/cognition/react.go:121-262`): builds a prompt with all registered tool JSON + a heuristic tool guide, asks for a structured JSON step, validates the tool name/params, calls `registry.Execute`, appends the observation, loops up to 3 iterations (actually at most **2 tool calls** — guard `len(callHistory) >= 2` at `:217-220`), then returns the final answer.

### 4.3 Tools

`registerBuiltinTools` (`cmd/mai/tool_registry.go:16-35`) registers 10 tools: `shell_execute`, `web_search`, `open_application`, `youtube_play`, `deep_search`, `web_research`, `file_write`, `get_system_time`, `whatsapp_send` (guarded fallback), `ui_automation`. Optional MCP tools are discovered at boot and wrapped in `MCPToolAdapter`. Registry lookups are RLock-protected; execution is lock-free. The WhatsApp tool only works inside an explicit ASR/chat turn (`UserTurnStart/End`) and only *prepares* a draft — sending requires confirmation.

### 4.4 Interruption

Two layers:
- **Hardware barge-in** (§3.2) sets `stopPlayback=1` and calls `orch.InterruptCurrent()`, which cancels the per-turn `currentCancel` registered in `handleConversation` (`loop.go:945-951`) — aborting the in-flight LLM HTTP stream.
- **Text interrupt** classifies "stop/cancel/emergency" as HIGH/CRITICAL (`internal/agent/interrupt.go:228-246`), fires `onInterrupt` → `InterruptCurrent()` + `agent.interrupt` bus event → `stopPlayback=1`.

**Gap:** the ReAct branch never registers `currentCancel`, and `HandleInput` runs on `context.Background()`, so barge-in cannot cancel ReAct tool execution. The soft-stop / queue / provider-managed policy machinery in `interrupt.go` is referenced only by tests — `softStop` is never armed in production and queued interrupts are never drained.

### 4.5 Supporting cognition

- **Memory**: `WorkingMemory` (bounded ring, 12k-char auto-compaction with async LLM summarization of dropped entries), `EpisodicStore` (SQLite `events`), `SemanticStore` (JSON snapshot + append-only JSONL + approximate search), `ProceduralStore` (success/failure patterns), `RAG` over semantic+episodic. Wired in `main.go:1376-1383`.
- **Personality**: `EmotionDetector` (7 emotions, keyword weights), `ProsodyAnalyzer` (RMS/ZCR/spectral centroid/pitch/variance/pause ratio), `TTSAdapter` (emotion → speed/pitch/volume). Prosody is ingested *before* the transcript event so text and voice emotion merge (`main.go:1851-1853`).
- **Proactive / goals / meta**: tickers every 2/5/10 min (`:283-303`) pattern-mine user actions, speak idle reminders, and self-analyze success rates. `GoalManager` is instantiated but only its pending count is read in production.
- **Session package**: `session.Manager`'s turn/generation APIs are **unused in production** — only `SetState`/`ObserveOverlap` are called on the audio path, purely for diagnostics.

### 4.6 Components that exist but are not wired

`Planner`, `Verifier`, `FunctionCaller`, `CognitionEngine` (interface), and most of `internal/observability` have **no production call sites**. README already concedes the verifier is "available but not wired"; the same is true of the planner and function caller. `internal/skills` *is* wired (contrary to the stale `TODO.md`).

## 5. Pipeline C — Companion / Avatar

### 5.1 Server surface (`internal/server/`)

- HTTP routes (`server.go:64-113`): `/ws`, `/api/health`, `/api/state`, `/` → `internal/server/static`, `/node_modules/` (three.js etc.), `/virtual/` → `transparent/web`, `/vrma/`, `/vrpack/`. Optional `Bearer`/`?token=` auth; check origin restricts to localhost.
- Protocol (`protocol.go:6-134`): JSON-RPC-style `WSMessage{id, method, params, result, error}`.
  - Client→server: `chat.input`, `audio.input`, `audio.input.start/stop`, `config.update`, `state.request`.
  - Server→client: `chat.response`, `status.changed`, `tts.chunk`, `emotion.detected`, `emotion.mai`, `asr.partial`, `asr.final`, `companion.action/dance/automation`, `config.changed`, `memory.update`.
- Hub (`hub.go`): one `Run()` select loop, per-client `readPump`/`writePump`, **non-blocking broadcast** (drops counted) because the event bus dispatches synchronously on the publisher's goroutine.
- Bridge (`bridge.go`): maps bus events → WS notifications, polls agent status every 500 ms.

### 5.2 Browser avatar (`internal/server/static/js/`)

- `index.html` loads Three.js + `@pixiv/three-vrm` via import map; PixiJS draws a procedural 2D room background behind the WebGL canvas.
- `character.js` (`CharacterRenderer`) loads `mai.vrm`, one idle VRMA clip, and 23 Motion3 JSON clips. Emotions → VRM blendshapes via `EMOTION_MAP`; liveliness via blink state machine, CPT saccades, mouse tracking, spring-damper head, breathing, micro-expressions.
- **Lip sync**: `buildVisemeSchedule` (`utils.js:37-155`) produces time-normalized vowel visemes from the response text; the backend repeats the sentence duration on every `tts.chunk`; `AudioPlayer` playhead + RMS analyser drive `character._updateLipSync` (`character.js:1190-1282`). Audio is mirrored **muted** to the tab when local speakers are authoritative — the tab only needs the shared timeline.
- `asr.partial/final` are published by the backend but the main UI has no handlers — no live caption in the browser.
- `character2d.js` is dead code (never loaded; also claims the same global).

### 5.3 Desktop overlay (`transparent/`)

Win32 layered, always-on-top WebView2 window hosting `/virtual/`. Native host handles transparency, dragging, click-through, perching, and scripted walking (`walkTo*` → `walkStart/walkEnd` events). `virtual.js` is a second, independent WS client using the same VRM + backend; it uses real VRMA clips for idle/walk/actions (the main UI mostly uses Motion3) and is the **only** consumer of `companion.automation` phases (WhatsApp choreography).

### 5.4 Vision / face tracking

`faceai/` is a standalone library (detector/embedder/recognizer, webcam loop, demo server) **not imported by the assistant**. `cmd/mai/vision.go` is Ollama screenshot→`[x,y]` element location for UI automation. Avatar "attention" comes from mouse/typing/presence and text-derived emotion — **no face landmarks reach the avatar**.

## 6. Support infrastructure

- **LLM** (`internal/llm/`): `Factory.CreateHybridProvider()` (`factory.go:85-120`) returns local-only Ollama when `hybrid_mode: false`; when true it builds local + cloud (openai/nvidia/openrouter/llamacpp/gemini/claude) + `PrivacyGuard`. `HybridProvider` routes non-sensitive prompts to cloud, sensitive to local — but once created it calls `guard.IsSensitive` directly and ignores `PrivacyGuard.ShouldUseLocal` (see §8).
- **Memory** (`internal/memory/`): four stores behind `MemoryManager`, RAG provider, runtime files under `data/`.
- **Tools/MCP** (`internal/tools/`): registry + 10 adapters + full JSON-RPC MCP client (disabled by default).
- **Skills** (`internal/skills/`): keyword-triggered manifest with 3 hardcoded starters (`plan_day`, `summarize`, `weekly_review`), optional `data/skills.json`, run through ReAct with episodic logging.
- **Events** (`internal/events/bus.go`): snapshot-based pub/sub, **synchronous** dispatch with per-handler panic recovery; `SubscribeAsync` and `RequestResponse` available. Synchronous dispatch is why the audio path hands frames off through a queue instead of doing work inside subscribers.
- **Config** (`pkg/models/config.go`): one `Config` struct; `config.yaml` sections audio/denoise/kws/vad/asr/tts/llm/vision/privacy/agentic/mcp/server.
- **Build/run** (`Makefile`): `build` → `mai.exe`; `companion` → `./mai.exe --companion`; `companion-virtual` additionally builds `transparent.exe`, waits on `/api/health`, then launches the overlay. Static paths are CWD-relative, so the server must be started from the repo root.

## 7. Cross-cutting design patterns

1. **Single-writer ownership** for shared state: one pipeline goroutine owns AEC/VAD/KWS/ASR; one ASR worker owns the decoder; one TTS renderer + one player own synthesis/playback. Other producers only enqueue.
2. **Synchronous event bus + queue handoff**: subscribers must be fast; slow work is moved behind channels (`submitAudioFrame`, `ttsSentCh`).
3. **Atomic flags with explicit ownership**: `ttsPlaying`, `stopPlayback`, `lastTTSEndNano`, `latestTurn` — documented as authoritative until a later duplex migration.
4. **Drop-oldest backpressure** everywhere audio is queued, with lag budgets derived from DSP constraints (AEC tap window), not arbitrary sizes.
5. **Interface-driven but monolithic**: clean interfaces in `pkg/interfaces` and `internal/*`, but `cmd/mai/main.go` is the de-facto wiring root and state machine.
