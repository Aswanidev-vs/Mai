# F1: Long-context prompt architecture for local/Ollama LLMs

Angle: Does a bigger `num_ctx` hurt inference / KV cache / RAM? How Ollama's context-length machinery works (defaults, env var, Modelfile, API), the KV-cache memory math, and practical model-class guidance for 128k–256k contexts on modest hardware.

## Findings

### [1] Ollama's documented default context window is 4096 tokens, but the FAQ's "4096" default is recent — the docs quoted 2048 as late as Jan 2025 and a Nov 2025 source still logs 4096 as the code default.
- quote: "By default, Ollama uses a context window size of 4096 tokens. ... This can be overridden with the `OLLAMA_CONTEXT_LENGTH` environment variable."
- url: https://docs.ollama.com/faq
- source_type: primary
- published: unknown (current docs as of 2026-08-09)
- confidence: high

Supporting history: a Jan 2025 GitHub issue quotes the then-current docs as "By default, Ollama uses a context window size of 2048 tokens" (https://github.com/ollama/ollama/issues/8356), and a Nov 2025 PR shows the server warning `using default ... value=8k default=4096` (https://github.com/ollama/ollama/pull/13248). So the effective default stepped 2048 → 4096 during 2025. The Modelfile reference still says `num_ctx ... (Default: 2048)` (https://docs.ollama.com/modelfile), i.e. the docs disagree with each other today.

### [2] `OLLAMA_CONTEXT_LENGTH` (server-wide env var) was added in Ollama PR #8938, merged 2025-02-24; the same PR states that per-request `num_ctx` is "expected to be moved away from in the future."
- quote: "For now, let users set a context length through `OLLAMA_CONTEXT_LENGTH` ... Users can still set `num_ctx` through the CLI or SDK on a request level but is expected to be moved away from in the future"
- url: https://github.com/ollama/ollama/pull/8938
- source_type: primary
- published: 2025-02-24
- confidence: high

Implication for the Go app: prefer booting the server with `OLLAMA_CONTEXT_LENGTH` or baking `PARAMETER num_ctx` into a custom Modelfile rather than relying on per-request `options` — the API path is being de-emphasized. The FAQ documents the ways context is set: env var at serve time, `/set parameter num_ctx` in `ollama run`, `options.num_ctx` in the API, and `PARAMETER num_ctx` in a Modelfile (https://docs.ollama.com/faq).

### [3] The newest official guidance auto-sizes context by VRAM: <24 GiB → 4k, 24–48 GiB → 32k, ≥48 GiB → 256k; agentic/long tasks officially recommended at ≥64,000 tokens.
- quote: "Ollama defaults to the following context lengths based on VRAM: * < 24 GiB VRAM: 4k context * 24-48 GiB VRAM: 32k context * >= 48 GiB VRAM: 256k context ... Tasks which require large context like web search, agents, and coding tools should be set to at least 64000 tokens."
- url: https://docs.ollama.com/context-length
- source_type: primary
- published: unknown (current docs; retrieved 2026-08-09)
- confidence: medium

This VRAM-scaled default page (contemporary, shown with newer models like gemma4) supersedes the flat "4096" of the FAQ — set your own context explicitly instead of trusting either default, since both pages are live simultaneously. Baseline for a voice companion targeting 165k–256k: you must pin `num_ctx` yourself; none of the defaults reach 128k except ≥48GiB hardware.

### [4] KV cache memory = 2 (K+V) × 2 bytes (f16) × num_layers × num_kv_heads × head_dim per token; it dominates RAM at long context (≈ one-third of the 7B model size at just 10k tokens).
- quote: "The memory required to store kv cache of one token is roughly `2 * 2 * num_layers * num_key_value_heads * head_dim`, where the first `2` accounts for keys and values and the second `2` is the number of bytes we need (assuming the model is loaded in `float16`). So if we have a context of length 10000 tokens, we would need `2 * 2 * 32 * 32 * 128 * 10000 ≈ 5GB`"
- url: https://huggingface.co/blog/kv-cache-quantization
- source_type: secondary
- published: 2024-05-16
- confidence: high

On a quantized-GGUF consumer machine the weights are small (e.g. Q4 7B ≈ 4–5 GB) but the f16 KV cache is not quantized by default, so KV cache quickly rivals or exceeds weights at ≥32k context.

### 4.1 (derived, same formula) Concrete sizes at 128k and 256k context (f16 KV cache):
- Qwen2.5-7B (fetched config: 28 layers, 4 KV heads; card at https://huggingface.co/Qwen/Qwen2.5-7B-Instruct-1M): 2×2×28×4×128 = 57,344 B ≈ 56 KiB/token → ~7.0 GiB @ 128k, ~14.1 GiB @ 256k.
- Llama 3.1/3.2 8B class (32 layers, 8 KV heads, head_dim 128 — standard config): 131,072 B = 128 KiB/token → ~16.0 GiB @ 128k, ~32 GiB @ 256k.
- With Ollama `q8_0` KV cache these halve (~3.5 / ~7.1 GiB for Qwen2.5-7B; ~8 / 16 GiB for 8B Llama), and `q4_0` quarters them.
- source_type: derived (arithmetic on primary config data + primary formula above)
- confidence: medium (formula and config cited; head_dim 128 assumed standard for the Llama-class row)

### [5] Ollama can quantize its K/V cache — `OLLAMA_KV_CACHE_TYPE` (default `f16`; `q8_0` ≈ half, `q4_0` ≈ quarter memory) — but only works with Flash Attention, is a global option, and hurts high-GQA models (e.g. Qwen2) most.
- quote: "OLLAMA_KV_CACHE_TYPE - The quantization type for the K/V cache. Default is `f16`. ... `q8_0` - ... uses approximately 1/2 the memory of `f16` with a very small loss in precision ... `q4_0` - ... uses approximately 1/4 the memory of `f16` ... Models that have a high GQA count (e.g. Qwen2) may see a larger impact on precision from quantization than models with a low GQA count."
- url: https://docs.ollama.com/faq ("How can I set the quantization type for the K/V cache?")
- source_type: primary
- published: unknown (current docs)
- confidence: high

The same page: "Currently this is a global option - meaning all models will run with the specified quantization type" and FA is auto-enabled "when the selected backend and devices support it" (`OLLAMA_FLASH_ATTENTION=1` to force). Flash Attention itself "can significantly reduce memory usage as the context size goes acts as the context window / grows." For a 165k–256k voice app this is the single highest-leverage knobs along with flash attention.

### [6] The big-`num_ctx` failure mode is KV spilloff/OOM, not math: bigger windows pre-allocate KV memory and can push the model off the GPU; Ollama's own guidance is to watch the processor split (avoid CPU offload) and check with `ollama ps`.
- quote: "Setting a larger context length will increase the amount of memory required to run a model. Ensure you have enough VRAM available to increase the context ... VERIFY evidence: For best performance, use the maximum context length for a model, and avoid offloading the model to CPU. Verify the split under `PROCESSOR` using `ollama ps`."
- url: https://docs.ollama.com/context-length
- source_type: primary
- published: unknown
- confidence: high

Community corollary (OOM with 16k ctx on a 24 GB 4090, fixed by lowering `num_batch` — the llama.cpp-bundled default is 512): "The default value is 512 (which is inherited from llama.cpp) and I found that reducing it finally solved the OOM problem ... PARAMETER num_batch 32" (https://github.com/ollama/ollama/issues/1800, Jan 2024). On modest hardware, a 128k–256k window exceeding VRAM silently moves layers to CPU and multiplies latency — the context "absolutely" affects latency only via this spill path (flash-attention mean `q8_0` KV makes full residency far more likely).

### [7] RAM scales linearly with (parallel requests × context): `OLLAMA_NUM_PARALLEL` defaults to 1, and per the FAQ "Required RAM will scale by OLLAMA_NUM_PARALLEL * OLLAMA_CONTEXT_LENGTH."
- quote: "OLLAMA_NUM_PARALLEL - The maximum number of parallel requests each model will process at the same time, default 1. Required RAM will scale by `OLLAMA_NUM_PARALLEL` * `OLLAMA_CONTEXT_LENGTH`."
- url: https://docs.ollama.com/faq
- source_type: primary
- published: unknown
- confidence: high

For interactive voice use (low concurrency), keep this at 1 so you're only paying one full KV budget; a 2k claim with 32k-ctx queued is a 16× KV allocation.

### [7] llama.cpp's KV-cache quantization lineage (PR #2969, Sept 2023) cites ~50% RAM/VRAM savings for the KV caches — the same q8_0 path Ollama exposes today.
- an entry: "Roughly 50% less RAM/VRAM usage for the KV cache, particularly relevant for long contexts and batched evaluation"
- quote: "Roughly 50% less RAM/VRAM usage for the KV cache, particularly relevant for long contexts and batched evaluation ... This PR aims to implement quantizing the KV cache as q8_0."
- url: https://github.com/ggml-org/llama.cpp/pull/2969
- source_type: community
- published: 2023-09-02
- confidence: medium

This PR was a PoC (perf -6% in its own benchmark) and was closed without merge; the feature landed upstream later, and Ollama's served `q8_0`/`q4_0` selection (finding [5]) is the user-facing consequence. Take the official Ollama numbers as ground truth, not this PR's timings.

### [8] Prompt eval (prefill) is where long context really bites on consumer hardware: without heavy tricks a 1M-token sequence needs custom kernels/sparse attention — vanilla local stacks (Ollama/llama.cpp) are realistically usable to ~128k, ~256k only just barely.
- quote: "Directly processing sequences of 1M tokens results in substantial memory overhead to store the activations in the projection layers, consuming 71GB of VRAM in Qwen2.5-7B. By integrating with chunked prefill after a chunk length of 32,768 tokens ... the activation VRAM usage is reduced by 96.7%. ... requires at least 120GB VRAM across the GPUs for the 7B ... 320GB for the 14B."
- url: https://qwenlm.github.io/blog/qwen2.5-1m/ (via the mirror fetched at https://huggingface.co/Qwen/Qwen2.5-7B-Instruct-1M)
- source_type: primary (vendor blog + card)
- published: 2025-01-27
- confidence: high

Same page quantifies the catch: sparse-attention MInference prefill = "3.2x to 6.7x acceleration ... for sequences of 1M token length", and the checkpoint is really trained for 256K ("The final instruction-tuned models are capable of handling sequences up to 256K tokens") with 1M done by Dual Chunk Attention length extrapolation, and "accuracy degradation may occur for sequences exceeding 262,144 tokens" on vanilla frameworks (HF card). The 1M-variant GGUF quantizations exist, but practical budget guidance for the companion: treat 128k as the comfortable long-context ceiling for 7B-class GGUF on consumer GPUs; 256k costs 2× KV and much slower prefill unless flash attention + q8_0 KV are in play.

### [9] Native context ceilings for the target model classes (use as num_ctx ceilings, tensors of which exceed them):
- Llama 3.1 8B/70B/405B: "Context length: 128k" all models (GQA), released 2024-07-23 — https://huggingface.co/meta-llama/Llama-3.1-8B-Instruct.
- Gemma 3: 4B/12B/27B accept "Total input context of 128K tokens ... and 32K tokens for the 1B size"; "Total output context of 8192 tokens" — https://huggingface.co/google/gemma-3-12b-it.
- Qwen2.5: standard 7B/14B Instruct = 131,072 tokens with YaRN support; the separate `-Instruct-1M` variants have yeasted/extrapolated 1M context but generation capped at 8192 tokens — https://huggingface.co/Qwen/Qwen2.5-7B-Instruct-1M.
- source_type: primary (model cards)
- confidence: high

### [10] The API surfaces what the runner did for prefill vs decode (`prompt_eval_count`/`prompt_eval_duration`, `eval_count`/`eval_duration` on /api/generate) — telemetry a Go client can use to watch long-context cost in the field.
- quote: "prompt_eval_count: Number of input tokens in the prompt / prompt_eval_duration: Time spent evaluating the prompt in nanoseconds / eval_count: Number of output tokens generated in the response / eval_duration: Time spent generating tokens in nanoseconds" (OpenAPI section of the generate reference; `options.num_ctx` = "Context length size (number of tokens)")
- url: https://docs.ollama.com/api/generate
- source_type: primary
- published: unknown
- confidence: high

Signal that prompt-eval (prefill) is usually the long-tail cost in the context: the HF KV blog also notes "the latency associated with generating the first token tends to be higher compared to subsequent tokens" and that prefill needs "the entire key-value matrices in one go for the whole input ... another memory bottleneck for long contexts" (https://huggingface.co/blog/kv-cache-quantization).
