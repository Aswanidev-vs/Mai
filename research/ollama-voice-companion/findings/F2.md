# F2: System prompt management in multi-step tool-calling loops — must the full system prompt + tools be re-sent every ReAct step, and how do providers order/cache/shrink prompts during the loop?

> ## Findings
> - [1] Yes — in a tool loop every step re-sends the full tools array plus the GROWING messages history (each step appends the assistant's tool_use and a tool_result block to the same list); nothing is dropped by the vendor, so the system prompt is naturally "re-sent" every step because the whole request is the system + tools + accumulating messages.
>   - quote: "We then send all of the tool definitions, the original prompt, the model's tool call, and the tool call output back to the model to finally receive a text response." and "With Responses, your application can continue this flow for as many tool calls as the task requires." Also: "Under the hood, functions are injected into the system message in a format the model has been trained on. This means callable function definitions count against the model's context limit and are billed as input tokens."
>   - url: https://platform.openai.com/docs/guides/function-calling
>   - source_type: primary
>   - published: continuously updated (fetched 2026-08-09)
>   - confidence: high
> - [2] Anthropic's loop contract is identical: request N+1 re-passes `tools`, the prior assistant `content` (its tool_use blocks), and a single user turn carrying the `tool_result`; keeping persona in the OpenAI system-message slot has no Anthropic equivalent — the tool-use system prompt is injected by the API automatically whenever `tools` is present.
>   - quote: "When you use `tools`, the API also automatically includes a special system prompt for the model that enables tool use" (Opus 5: ~286 extra tokens for `tool_choice: auto`, ~406 for `any`/`tool`).
>   - url: https://docs.anthropic.com/en/docs/build-with-claude/tool-use
>   - source_type: primary
>   - published: continuously updated (fetched 2026-08-09)
>   - confidence: high
> - [3] Both vendors converge on the same ordering rule to make each loop step hit the cache: static/instructional content (system/persona, tools, few-shot examples) first, variable content (transferring user message, timestamp, latest tool results) last.
>   - quote: "Cache hits are only possible for exact prefix matches within a prompt. To realize caching benefits, place static content like instructions and examples at the beginning of your prompt, and put variable content, such as user-specific information, at the end. This also applies to images and tools, which must be identical between requests." (OpenAI) and "Cache prefixes are created in the following order: `tools`, `system`, then `messages`." / "Place static content (tool definitions, system instructions, context, examples) at the beginning of your prompt." (Anthropic)
>   - urls: https://platform.openai.com/docs/guides/prompt-caching | https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching
>   - source_type: primary
>   - published: continuously updated (fetched 2026-08-09)
>   - confidence: high
> - [4] Do not mutate the tools array mid-loop: any change to tool schemas invalidates the entire prompt cache (tools → system → messages hierarchy), while OpenAI explicitly designed `tool_choice: allowed_tools` so you can restrict which tools the model may call per step without touching the tools list and thereby keep cache hits.
>   - quote: "Modifying tool definitions (names, descriptions, parameters) invalidates the entire cache" (Anthropic); "You might want to configure an `allowed_tools` list in case you want to make only a subset of tools available across model requests, but not modify the list of tools you pass in, so you can maximize savings from prompt caching" (OpenAI).
>   - urls: https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching | https://platform.openai.com/docs/guides/function-calling
>   - source_type: primary
>   - published: continuously updated (fetched 2026-08-09)
>   - confidence: high
> - [5] Anthropic's caching design is literally built for this loop shape: automatic cache breakpoint "moves forward as conversations grow", so request N reads tools+system+all prior turns from cache and only re-tokenizes the new tail — this is the provider-native way to keep a full system prompt on every step at ~10% of base input token cost (cache reads 0.1×).
>   - quote: "The system automatically applies the cache breakpoint to the last cacheable block and moves it forward as conversations grow. Best for multi-turn conversations where the growing message history should be cached automatically."
>   - url: https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching
>   - source_type: primary
>   - published: continuously updated (fetched 2026-08-09)
>   - confidence: high
> - [6] Long loops break naive single-breakpoint caching: Anthropic cache reads look back only 20 blocks per breakpoint, so an agent that appends many assistant/tool-result blocks per turn eventually outruns the lookback and silently loses cache hits — the documented fix is a second (or up to 4 total) explicit `cache_control` breakpoint placed earlier, and 5-minute default TTL means steps must land within ~5 min of each other.
>   - quote: "The lookback window is 20 blocks … check 20 positions per breakpoint … If a growing conversation pushes your breakpoint 20 or more blocks past the last cache write, the lookback window misses it. Add a second breakpoint closer to that position from the start."
>   - url: https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching
>   - source_type: primary
>   - published: continuously updated (fetched 2026-08-09)
>   - confidence: high
> - [7] On GPT-5.6-family models OpenAI's implicit cache breakpoint sits on the latest user/tool message — exactly the part that changes every loop step — so with only implicit caching the loop can report `cached_tokens: 0` while sharing thousands of tokens with prior steps; the documented remedy is an explicit `prompt_cache_breakpoint` at the end of the stable prefix (persona/system/tools) plus a stable `prompt_cache_key`.
>   - quote: "If the implicit breakpoint includes that changing content, the full prefix at the breakpoint differs between requests. As a result, `cached_tokens` can be `0` even though the requests share thousands of identical tokens, and the service can repeatedly write the changing prefix to cache. To reuse the shared content, add an explicit `prompt_cache_breakpoint` at the end of the stable prefix and set the same `prompt_cache_key` on requests that share it."
>   - url: https://platform.openai.com/docs/guides/prompt-caching
>   - source_type: primary
>   - published: continuously updated (fetched 2026-08-09)
>   - confidence: high
> - [8] History-window management during long loops is a developer responsibility on every framework: LangChain's agent state is "append-only: new messages are added, never replaced", so the full thread is replayed against each step by default; the ecosystems' standard strategies are compress (auto-summarize) and trim (drop oldest), later run below the window budget.
>   - quote: "`messages`: contains the full conversation history for the current thread. Append-only: new messages are added, never replaced." and "Claude Code runs 'auto-compact' after you exceed 95% of the context window and it will summarize the full trajectory of user-agent interactions." Context-trimming "can use hard-coded heuristics like removing older messages from a list."
>   - urls: https://docs.langchain.com/oss/python/langchain/agents | https://www.langchain.com/blog/context-engineering-for-agents
>   - source_type: primary
>   - published: 2025-07-02 (blog) / continuously updated (docs; fetched 2026-08-09)
>   - confidence: high
> - [9] Persona need not be a bloated system prompt — the design pattern from LllamaIndex/LangChain scaffolding is: (i) a short static block with identity that is always inserted into the system prompt, and (ii) history beyond a token budget that is flushed/summarized/vectorized instead of being replayed verbatim; persona continuity comes from the static block + selective memory, not from re-reading whole old turns.
>   - quote: "[System] short-term memory stores the last X messages that fit into a token limit" with `chat_history_token_ratio` (default 0.7) and `token_flush_size` (default 3000); "[StaticMemoryBlock] information will always be inserted into the memory" and blocks insert into the system message by default (`insert_method="system"`); the deprecated-but-documented `ChatSummaryMemoryBuffer` "summarizes the conversation periodically when it gets too long."
>   - url: https://developers.llamaindex.ai/python/framework/module_guides/deploying/agents/memory/index.md
>   - source_type: primary
>   - published: continuously updated (fetched 2026-08-09)
>   - confidence: high
> - [10] There is no fetched vender guidance stating a shorter system prompt itself will break persona — providers treat identity/persona as stable prefix content (cached, cheap to re-read) and treat the loop's boundaries with execution guards instead: cap loop iterations and keep the static prefix byte-identical across steps; for local Ollama (no provider-side KV cache) the same "static-first, keep-it-stable" ordering minimizes how many prefix tokens are re-processed each step — this last clause is inference, not a fetched quote.
>   - quote: "it's also common to include stopping conditions (such as a maximum number of iterations) to maintain control" and "it's crucial for the agents to gain 'ground truth' from the environment at each step (such as tool call results) to assess its progress" (Anthropic); "An agent is a model calling tools in a loop until a given task is complete" (LangChain); on context growth: "long-running tasks … can balloon cost/latency, or degrade agent performance" (LangChain blog).
>   - urls: https://www.anthropic.com/research/building-effective-agents | https://docs.langchain.com/oss/python/langchain/agents | https://www.langchain.com/blog/context-engineering-for-agents
