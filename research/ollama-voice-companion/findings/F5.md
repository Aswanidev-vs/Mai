# F5: RAG efficiency on low-end hardware — batching, skip-RAG, and token budgets

## Findings

- [F1] Batch embedding: Ollama `/api/embed` takes `input` as a single string OR an array of strings and returns one vector per item in a single HTTP request — this is the native batching mechanism.
  - quote: "input: oneOf: string | array of strings — Text or array of texts to generate embeddings for"
  - url: https://docs.ollama.com/api/embed
  - source_type: official Ollama API docs
  - published: docs current as of fetch 2026-08-09
  - confidence: high

- [F2] Why batches amortize on low-end hardware: the response exposes `load_duration` and `total_duration` in nanoseconds plus `prompt_eval_count`, so the model-load/HTTP fixed cost is paid once per request, not once per text. Ollama keeps a loaded model in memory for 5 minutes by default (`keep_alive`), so per-call embedding also amortizes over the warm model; preloading with an empty request (`curl -d '{"model": "..."}'`) removes load latency entirely.
  - quote: "By default models are kept in memory for 5 minutes before being unloaded. This allows for quicker response times if you're making numerous requests to the LLM."
  - url: https://docs.ollama.com/faq
  - source_type: official Ollama docs (FAQ)
  - published: fetched 2026-08-09
  - confidence: high

- [F3] Batching CONFLICTS with parallelism: Ollama's default parallelism is 1; raising `OLLAMA_NUM_PARALLEL` multiplies the context ("a 2K context with 4 parallel requests will result in an 8K context and additional memory allocation"). On modest RAM/GPU the frugal pattern is one big `input` array per over the wire, not parallel per-item requests.
  - quote: "Parallel request processing for a given model results in increasing the context size by the number of parallel requests. For example, a 2K context with 4 parallel requests will result in an 8K context and additional memory allocation."
  - url: https://docs.ollama.com/faq
  - source_type: official Ollama docs (FAQ)
  - published: fetched 2026-08-09
  - confidence: high

- [F4] Embedding model sizing for low-end: `nomic-embed-text` (old tag 137M params) ships in Ollama at 274MB, dim 768, and per the Nomic card supports Matryoshka dimensionality reduction — 768 dims MTEB 62.28, 512→61.96, 256→61.04, 128→59.34 — so vectors can be shrunk for storage/BRAM with negligible quality loss. Ollama's `/api/embed` exposes a `dimensions` parameter for this. `bge-m3` (xlm-roberta-based, 567M params, 1.2GB in Ollama, dim 1024, 8K context) is ~4.5x heavier and multilingual — only worth it if multilingual retrieval is a hard requirement.
  - quote: "Model size 0.1B params" / "nomic-embed-text:latest 274MB · 2K context window" / "bge-m3:latest 1.2GB · 8K context window"
  - url: https://huggingface.co/nomic-ai/nomic-embed-text-v1.5 ; https://ollama.com/library/nomic-embed-text ; https://ollama.com/library/bge-m3
  - source_type: HuggingFace model card + Ollama model library
  - published: nomic v1.5 card (2024), bge-m3 paper arXiv Feb 2024
  - confidence: high for specs; latency claims are sizing-only (no CPU benchmark numbers found)

- [F5] Truncation silently degrades embeddings: in `/api/embed`, `truncate` defaults to true — inputs exceeding the context window are silently truncated. With `truncate: false` the API returns a error instead. For retrieval quality, chunk-to-size and set `truncate:false` so over-long inputs fail loudly rather than quietly embedding the document head.
  - quote: "If true, truncate inputs that exceed the context window. If false, returns an error. (default: true)"
  - url: https://docs.ollama.com/api/embed
  - source_type: official Ollama API docs
  - published: fetched 2026-08-09
  - confidence: high

- [F6] Query/document prefix rule differs by model: nomic-embed-text mandates a task instruction prefix (`search_document: ...` for indexing, `search_query: ...` for queries) — omitting it silently harms retrieval. BGE-M3 explicitly requires NO query prefix ("the BGE-M3 model no longer requires adding instructions to the queries"). A voice companion must hard-code the correct prefix for whichever model it picks.
  - quote: "the text prompt must include a task instruction prefix… if you are implementing a RAG application, you embed your documents as `search_document: <text here>` and embed your user queries as `search_query: <text here>`" — and "the BGE-M3 model no longer requires adding instructions to the queries."
  - url: https://huggingface.co/nomic-ai/nomic-embed-text-v1.5 ; https://huggingface.co/BAAI/bge-m3
  - source_type: HuggingFace model cards
  - published: 2024
  - confidence: high

- [F7] Skip-RAG evidence — stuffing degrades answers even on frontier models: Chroma's Context Rot study (18 models incl. Qwen3) measured retrieval QA on focused vs full inputs: focused prompts (~300 tokens) always beat full prompts (~113k-token histories) across every model family, and adding even a single distractor reduces performance further. Implication for a voice companion: greet/small-talk/intent-answerable turns should bypass retrieval entirely; a simple router (intent + confidence threshold + cached-answer hit) avoids paying both embed latency and attention-budget cost.
  - quote: "Across all models, we see significantly higher performance on focused prompts compared to full prompts." / "Adding irrelevant context, and thereby adding an additional step of retrieval, significantly impacts a model's ability to maintain reliable performance."
  - url: https://research.trychroma.com/context-rot
  - source_type: Chroma technical report
  - published: July 14, 2025
  - confidence: high (empirical finding), medium (the router design is the author's inference from it)

- [F8] Authoritative tool data should bypass RAG: Pinecone recommends full-text/BM25 (lexical) search when relevance is exact keyword/ID/entity based, and dense semantic search for paraphrase-style questions; the two can be hybrid with sparse vectors. Similarly, Anthropic advises returning token-efficient authoritative data from tools rather than symmetric retrieval. Design rule: when the user query maps to an authoritative tool result (calendar, alarms, sensor state), return the tool's data directly and do not mix it with retrieved chunks.
  - quote: "When relevance depends on exact keyword or phrase matches over text content — for example, product names, technical IDs, named entities, or jargon — we recommend full-text search. It uses BM25 ranking." — "the most common failure modes we see is bloated tool sets that cover too much functionality… keeping context informative, yet tight"
  - url: https://docs.pinecone.io/guides/optimize/increase-relevance.md ; https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
  - source_type: vendor docs + Anthropic engineering article
  - published: Pinecone fetched 2026-08-09; Anthropic Sep 29, 2025
  - confidence: medium

- (c) Token budget — context defaults are the trap: Ollama's Modelfile docs state `num_predict` default `-1` (infinite generation) and `num_ctx` default `2048` (the FAQ says the default context is 4096 — docs disagree, treat as 2048–4096), with newer context-length guide selecting 4k/32k/256k by VRAM. Consequences: (1) output tokens are NOT reserved unless the companion sets `num_predict`/reserved text; (2) on a 4k window, stuffing "retrieved chunks + full history + system" can overflow and cause silent truncation in generate/chat — the same reason Ollama exposes explicit truncation in embedding. On low RAM, run via quantized K/V cache.
  - quote: "num_predict — Maximum number of tokens to predict when generating text. (Default: -1, infinite generation)" and "By default, Ollama uses a context window size of 4096 tokens."
  - url: https://docs.ollama.com/modelfile ; https://docs.ollama.com/faq ; https://docs.ollama.com/context-length
  - source_type: official Ollama docs
  - published: fetched 2026-08-09
  - confidence: high (numbers); note doc-internal inconsistency 2048 vs 4096

- [F10] Fractional budget reference points: Anthropic's thematic of context windows vs max-output (e.g., Claude Haiku 4.5: 200k context / 64k max-0ut-tokens = ~32% reserved; Claude Sonnet/Opus 5: 1M context / 128k max output = ~13% reserved) shows even frontier APIs set output at 13–32% of the window, and Anthropic's general rule is "find the *smallest* possible set of high-signal tokens" for the input side. For a 7B model on modest hardware with a ~4-8k usable window, a working rule is: context budget = system (small, instructions-first) + retrieval (the minimal `search_query`-prefixed hits needed to answer) + rolling summary/history, with output reserved separately via a fixed `num_predict`. I could not fetch a page containing exact "system 10% / context 50%" fractions; those zones are community lore and need local (loss) calibration.
  - quote: "good context engineering means finding the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome" / "Max output 128k tokens" at "1M token" context
  - the URL(s): https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents ; https://platform.claude.com/docs/en/about-claude/models/overview
  - source_type: Anthropic engineering + model docs
  - published: Sept 29, 2025 / current
  - confidence: high for principles, low for the specific 10%/50% figures (not found).
